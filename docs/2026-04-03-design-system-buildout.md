# Design System Build-Out — PRD

**Date:** 2026-04-03
**Status:** Approved
**Approach:** Foundation-Up (7 phases, sequential with CI running in parallel from Phase 1)

## Overview

Build out the PRD Platform's UI design system from its current ~25% alignment to full PRD compliance. The system adopts a four-tier component architecture, a Style Dictionary token pipeline (structured for future W3C DTCG migration), AI-ready component and asset registries with MCP integration, and a Claude Code skill ensuring all agents and subagents build within the system's constraints.

### Decisions Made

- **Phasing:** Foundation-Up — token pipeline first, then architecture, registries, AI, CI, generative UI.
- **Design workflow:** Hybrid (code-first with some Figma). Tokens live in code, optionally export to Figma.
- **Framework target:** Next.js 15.3 + React 19. No Next.js 16 dependency.
- **Effects tier:** Included as a fourth tier (`effects/`) for animated/marketing components.
- **Token format:** Style Dictionary now, structured for DTCG migration later.
- **Registry delivery:** Static JSON as source of truth + MCP server wrapper for live querying.
- **Accessibility gate:** Hard gate. axe-core failures block PRs. No grace period.
- **Agent awareness:** Claude Code skill + MCP auto-discovery via `.mcp.json`.

## Phase 1: Token Pipeline

### Token Source

File: `design-tokens/tokens.json` (Style Dictionary format).

Token categories follow the `--ds-{category}-{element}` naming convention (the `ds-` prefix avoids collision with shadcn's `--color-*` vars during migration):

| Category | Tokens |
|---|---|
| `brand` | `primary`, `secondary`, `accent`, `neutral` |
| `surface` | `background`, `elevated`, `sunken`, `overlay` |
| `text` | `primary`, `secondary`, `muted`, `inverse`, `link` |
| `border` | `default`, `strong`, `subtle` |
| `status` | `success`, `warning`, `error`, `info` |
| `radius` | `none`, `soft`, `medium`, `full` |
| `spacing` | `xs`, `sm`, `md`, `lg`, `xl`, `2xl` |
| `shadow` | `sm`, `md`, `lg` |
| `motion` | `fast`, `normal`, `slow` |

### Theme Support

Three themes defined as separate token sets in `tokens.json`:
- `light` (default)
- `dark`
- `high-contrast`

Each theme applied via `[data-theme]` CSS custom property overrides.

### Pipeline Outputs

Generated by Style Dictionary during CI:
- `src/styles/tokens.css` — CSS custom properties
- `src/styles/tokens.ts` — TypeScript constants + type definitions
- `src/styles/tokens.json` — JSON for Figma/external tools

### Tailwind Integration

Generated `tokens.css` imported in `globals.css`, mapped via Tailwind v4 `@theme` block. All existing hardcoded values in `globals.css` migrated to token references.

### Migration

Current 25 CSS custom properties (24 `--color-*` plus `--radius`) mapped to new semantic names. Old names aliased temporarily via CSS fallbacks in the `@theme` block, then removed after all components update references.

### DTCG Migration Path

Token structure in `tokens.json` uses nested category/item/variant hierarchy compatible with DTCG's `$value`/`$type` schema. When DTCG tooling matures, conversion is a schema transform, not a restructure.

## Phase 2: Four-Tier Component Architecture

### Directory Structure

```
src/components/
├── ui/              # Tier 1: Pristine shadcn/ui primitives (Radix-based)
├── primitives/      # Tier 2: Domain-agnostic compositions
├── features/        # Tier 3: Product-level compositions
└── effects/         # Tier 4: Animated/marketing components
```

### Tier 1 — `ui/` (Pristine Primitives)

- Managed exclusively via `npx shadcn@latest add`
- No manual edits — styling overrides happen only through tokens in `globals.css`
- Current 13 components (button, card, badge, dialog, tabs, etc.) remain here
- CVA variant definitions remain but resolve to token values, not hardcoded colors

### Tier 2 — `primitives/` (Domain-Agnostic Compositions)

Lightly composed components with project-specific defaults. No product domain references.

Initial components to create:
- `SearchableSelect` — select + command/combobox pattern
- `DataTable` — table + sorting + pagination
- `ConfirmDialog` — dialog + button with confirm/cancel pattern
- `FormField` — label + input + error message composition
- `IconButton` — button + lucide icon with standardized sizing

### Tier 3 — `features/` (Product-Level Compositions)

Migrate existing root-level product components:
- `sidebar.tsx` → `features/Sidebar/`
- `template-card.tsx` → `features/TemplateCard/`
- `brand-card.tsx` → `features/BrandCard/`
- `monaco-editor.tsx` → `features/MonacoEditor/`

### Tier 4 — `effects/` (Animated/Marketing)

Isolated tier for non-functional visual effects:
- Aurora backgrounds, gradient animations
- Beam/sparkle effects
- Scroll-triggered animations
- Parallax sections

All marked `"use client"`. Tree-shakable. Never required by core product pages.

### Import Boundary Rules

| Tier | Can Import From |
|---|---|
| `ui/` | External packages only |
| `primitives/` | `ui/`, external packages |
| `features/` | `primitives/`, `ui/`, external packages |
| `effects/` | `ui/`, external packages |

`features/` cannot import from other `features/` — shared logic goes to `primitives/`.

### Component File Convention

Tiers 2–4 use directory-per-component:

```
primitives/SearchableSelect/
├── index.ts              # Public export
├── SearchableSelect.tsx  # Implementation
└── SearchableSelect.test.tsx  # Tests (including axe-core)
```

Tier 1 (`ui/`) keeps flat file structure (shadcn CLI manages it).

## Phase 3: Asset & Component Registries

### Asset Registry — `src/assets/registry.json`

Auto-generated by CI script scanning `src/assets/`, enriched with manually authored metadata from `src/assets/metadata.yaml`.

Schema per entry:

```json
{
  "name": "bulletproof-mark",
  "file": "brands/bulletproof/mark.svg",
  "category": "brand",
  "tags": ["logo", "bulletproof", "icon"],
  "usage": "Brand mark for Bulletproof Software identity",
  "format": "svg",
  "size": "1.2KB"
}
```

Lucide React remains the canonical icon library. The asset registry catalogs custom icons only — Lucide icons discovered via package introspection.

Assets without metadata entries flagged as incomplete in CI.

### Component Registry — `src/components/registry.json`

Full prop/variant/composition metadata for every component across all four tiers.

Schema per entry:

```json
{
  "name": "Button",
  "tier": "ui",
  "path": "components/ui/button.tsx",
  "description": "Primary action trigger with semantic variants",
  "client": false,
  "props": [
    {
      "name": "variant",
      "type": "'default' | 'destructive' | 'outline' | 'secondary' | 'ghost' | 'link'",
      "default": "default",
      "description": "Visual style variant"
    }
  ],
  "tokens": ["--brand-primary", "--radius-soft"],
  "dependencies": ["@radix-ui/react-slot", "class-variance-authority"],
  "examples": [
    {
      "label": "Primary action",
      "code": "<Button variant=\"default\">Save Changes</Button>"
    }
  ],
  "accessibility": {
    "role": "button",
    "keyboard": ["Enter", "Space"],
    "notes": "Inherits Radix Slot forwarding for asChild composition"
  }
}
```

### Registry Generation

Script: `scripts/generate-registry.ts`

Parses component source files via AST to extract:
- Exported prop types (TypeScript interfaces/types)
- CVA variants
- Import dependencies
- `"use client"` directive presence

Manually authored fields (description, examples, accessibility notes) live in `registry-meta.yaml` and get merged during generation. Missing manual metadata flags a CI warning.

### CI Validation

- JSON Schema validation on every PR
- Stale entries (component file deleted but registry entry remains) fail the build
- Missing metadata entries produce warnings (not failures)

## Phase 4: MCP & AI Integration

### MCP Server — `src/mcp/design-system-server.ts`

Declared in project `.mcp.json` for automatic Claude Code discovery:

```json
{
  "mcpServers": {
    "design-system": {
      "command": "npx",
      "args": ["tsx", "src/mcp/design-system-server.ts"],
      "env": {}
    }
  }
}
```

### MCP Tools

| Tool | Input | Output |
|---|---|---|
| `get_component` | `{ name: string }` | Full registry entry with props, variants, examples, a11y notes |
| `search_components` | `{ query: string, tier?: string }` | Matching components ranked by relevance |
| `get_asset` | `{ name: string }` | Asset metadata + file path |
| `get_tokens` | `{ category?: string, theme?: string }` | Token values, optionally filtered |
| `get_composition_rules` | `{ tier: string }` | Import rules and constraints for the tier |

All tools are read-only. No mutations through MCP — all changes go through code + CI.

### AI Context File

Auto-generated file at `src/components/ai-context.md` containing:
- Token names and semantic meanings
- Component inventory with tier, props, and composition rules
- Import conventions per tier
- Example patterns showing correct component composition

Referenced in `.cursorrules` (Cursor) and passed as system context for v0 generation.

## Phase 5: CI Enforcement

### ESLint Configuration — `eslint.config.mjs`

**Import boundary rules** (via `eslint-plugin-import`):
- `ui/` cannot import from `primitives/`, `features/`, or `effects/`
- `primitives/` cannot import from `features/` or `effects/`
- `features/` cannot import from `effects/` or other `features/`
- `effects/` cannot import from `primitives/` or `features/`

**Token enforcement:**
- Flag hardcoded color values (hex, rgb, hsl) in component files
- Flag hardcoded spacing/radius pixel values in component files

**Hydration safety:**
- Flag bare `window`, `document`, `localStorage` access outside `useEffect`, event handlers, or `typeof window` guards in files not marked `"use client"`
- Flag `"use client"` in `ui/` tier (unless Radix requires it)

### Accessibility — Hard Gate

**Component-level:** `jest-axe` tests required for every component in `primitives/` and `features/`:

```tsx
import { axe } from 'jest-axe';

it('has no accessibility violations', async () => {
  const { container } = render(<SearchableSelect options={mockOptions} />);
  expect(await axe(container)).toHaveNoViolations();
});
```

**Page-level:** Playwright + axe-core integration runs against rendered pages on every PR. Any violation blocks the PR.

### CI Pipeline — `.github/workflows/ci.yml`

```
Steps:
1. checkout + setup Node 20
2. npm ci
3. npm run typecheck           (existing)
4. npm run lint                 (NEW — ESLint with all rules)
5. npm run test                 (NEW — Jest with jest-axe)
6. npm run generate:registry    (NEW — regenerate + validate registries)
7. npm run generate:tokens      (NEW — Style Dictionary build + drift check)
8. npm run build                (existing)
9. npm run test:a11y            (NEW — axe-core page audit via Playwright)
```

Steps 3–7 run in parallel. Steps 8–9 sequential (build then audit).

### Pre-commit Hook

Via `husky` + `lint-staged`:
- ESLint on changed `.ts/.tsx` files
- Token drift check (compares hash of `tokens.json` against last generated output)

## Phase 6: Generative UI

### Component Generator CLI

Script: `scripts/generate-component.ts`

```bash
npm run generate -- "a card that shows a user's subscription status with renewal date and upgrade button"
```

Behavior:
1. Parses description to determine correct tier (product domain → `features/`, reusable pattern → `primitives/`, animation → `effects/`)
2. Reads `registry.json` to identify existing components for composition
3. Generates component directory: `index.ts`, `ComponentName.tsx`, `ComponentName.test.tsx` (with axe-core test)
4. Updates `registry-meta.yaml` with placeholder entry

AI backend: Claude API with registry + token context as system prompt. Falls back to template-based scaffold if no API key configured.

Guard rails:
- Generated code must pass ESLint import boundary rules before writing to disk
- Generated code uses only token values
- Human review required before commit — script outputs files but does not `git add`

## Phase 7: Claude Code Skill & Agent Awareness

### Design System Skill — `design-system`

**Triggers:**
- User asks to "create a component", "build a page", "add UI", "design a feature"
- Any task involving `.tsx` files in `src/components/`
- Mentions of styling, theming, tokens, or design patterns

**Skill content provides agents with:**

1. **Architecture rules** — four-tier structure, import boundaries, tier selection guidance
2. **Token vocabulary** — available semantic tokens by category, how to reference them
3. **Component discovery** — query MCP (`get_component`, `search_components`) before building anything new
4. **Scaffold command** — use `npm run generate` for new components instead of writing from scratch
5. **Accessibility requirement** — every new component must include an axe-core test
6. **Registry update** — after creating a component, add metadata to `registry-meta.yaml`

**Agent behavior enforcement (explicit overrides in skill):**
- "Do not create a component that already exists." — Always `search_components` first.
- "Do not use hardcoded colors, spacing, or radii." — Always `get_tokens` to find the right token.
- "Do not put components in the wrong tier." — Always `get_composition_rules` for the target tier.
- "Do not skip the accessibility test." — Every new component gets a `jest-axe` test.

### MCP Auto-Discovery

The MCP server declared in `.mcp.json` is automatically available to all Claude Code sessions in this repo. Agents and subagents inherit access — no per-session configuration needed.

### Subagent Context Propagation

When the main agent dispatches subagents for UI work, the skill instructs including this context in the subagent prompt:

> "This project uses a four-tier design system with an MCP server at `design-system`. Before creating or modifying any component, call `search_components` to check existing inventory and `get_tokens` for available design tokens. Follow the composition rules for the target tier. All components require axe-core accessibility tests."

## Security Considerations

| Concern | Mitigation |
|---|---|
| Dependency drift in vendored components | Dependabot scanning + weekly CI comparison against upstream advisories |
| SVG injection via uploaded assets | DOMPurify sanitization before storage; CSP restricts inline SVG |
| Token exposure | Tokens contain no secrets; pipeline runs in CI only |
| XSS in AI-generated output | ESLint security rules + manual review gate before merge |
| Theme manipulation | `data-theme` validated against allowlist (`light`, `dark`, `high-contrast`) |
| Asset/registry tampering | JSON Schema validation in CI; changes require PR review |
| MCP server access | Read-only tools; no mutation endpoints; localhost-only binding |
